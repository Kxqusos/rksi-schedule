# План: строгая послойная архитектура backend (apps/api)

Статус: черновик на ревью. Не реализовано — это план для обсуждения и правок перед началом работ.

## 1. Зачем

Текущий код (роутер → сервис → `session.scalar(select(...))` напрямую) работает, но смешивает слои:

- Pydantic-схемы (`ScheduleProblemResponse`, `LessonMutationResult` и т.п.) строятся прямо внутри файлов с бизнес-логикой (`services/schedule_editor/service.py`), вместо того чтобы сервис отдавал доменные объекты, а схема собиралась отдельно.
- SQL-запросы (`session.scalar(select(...))`) разбросаны по сервисным функциям без отдельного слоя доступа к данным — сложно переиспользовать, тестировать и оптимизировать (N+1) изолированно от бизнес-правил.
- `Engine`/пул соединений к БД создаётся заново на каждый HTTP-запрos (`build_session_factory()` вызывается в каждом роутере) — это и архитектурная, и эксплуатационная проблема при нагрузке.
- Не все домены оформлены одинаково: `schedule_editor/` и `import_schedule/` — папки с `service.py`, а `groups.py`, `rooms.py`, `teachers.py`, `time_profiles.py`, `users.py` — плоские файлы. Нет единого шаблона, по которому добавлять новый домен.

Функционал ещё не закончен (планируются дальнейшие фичи поверх групп/time_profiles/расписания) — сейчас удобный момент закрепить единый шаблон, по которому будет добавляться весь будущий код, а не рефакторить тысячи строк позже.

Нагрузка, под которую считаем (см. предыдущее обсуждение): ~5-6 тыс. студентов, две смены (1-3 и 4-7 пара), пиковые всплески запросов к публичному просмотру расписания между парами и в начале смен, хранение полного учебного года (~300k строк `lessons`).

## 2. Слои и направление зависимостей

```
routers/        →  schemas (request/response DTO)
                 →  services (use-case функции, Depends(get_session))
                 →  repositories (SQL-запросы, возвращают ORM-модели)
                 →  models (SQLAlchemy ORM)

mappers/         используются routers'ом: domain/ORM → schemas (response)
```

Жёсткое правило зависимостей (проверяется на код-ревью, не тулингом — в проекте нет линтера границ слоёв, заводить его не предлагаю, это overkill для текущего размера):

- **`repositories/`** — только SQLAlchemy. Не импортирует `schemas`. Не содержит бизнес-правил (никаких "если группа без классного часа — пропустить" здесь, только запросы и фильтры). Возвращает ORM-модели или примитивы.
- **`services/`** — бизнес-правила и оркестрация. Импортирует `repositories` и `models`, **не импортирует `schemas`**. Возвращает простые `@dataclass`-объекты (уже есть прецедент: `LessonMutationResult`, `Actor`) — это "доменный результат", а не HTTP-форма ответа.
- **`mappers.py`** (новый, один на домен) — единственное место, где встречаются `schemas` и доменные dataclass/ORM-объекты. Чистые функции `def to_response(domain_obj) -> SomeResponseSchema`.
- **`routers/`** — вызывает `service`, прогоняет результат через `mapper`, переводит доменные исключения в `HTTPException`. Никакого SQL и pydantic-логики внутри.
- **`schemas/`** — как сейчас, чистые Pydantic DTO без логики.

Никаких плоских файлов-сервисов больше не заводить (текущие плоские — `groups.py`, `rooms.py`, `teachers.py`, `time_profiles.py`, `users.py` — переносятся в папки в рамках этого рефакторинга, не оставляются как "пока сойдёт").

## 4. DB engine/session — убрать пересоздание на запрос

Сейчас (`db/session.py`):

```python
def build_session_factory(database_url: str):
    engine = create_engine(database_url, future=True)
    return engine, sessionmaker(bind=engine, ...)
```

вызывается в **каждом** эндпоинте. Целевая схема:

```python
# db/engine.py
_engine: Engine | None = None
_session_factory: sessionmaker | None = None

def init_engine(database_url: str) -> None:
    global _engine, _session_factory
    _engine = create_engine(database_url, future=True, pool_size=10, max_overflow=20, pool_pre_ping=True)
    _session_factory = sessionmaker(bind=_engine, autoflush=False, expire_on_commit=False)

def dispose_engine() -> None:
    if _engine is not None:
        _engine.dispose()
```

```python
# db/session.py
def get_session() -> Generator[Session, None, None]:
    with _session_factory() as session:
        yield session
```

`main.py`: `lifespan` зовёт `init_engine(get_database_url())` при старте и `dispose_engine()` при остановке — один `Engine`/пул на процесс, а не на запрос.

Роутеры: вместо ручного `build_session_factory(database_url)` — `session: Session = Depends(get_session)` в сигнатуре эндпоинта. Тесты, которые сейчас подставляют `app.state.database_url` индивидуально в каждом тестовом файле (`test_groups.py`, `test_auth_users.py` и т.д. — общего фикстура в `conftest.py` для этого пока нет), переключаются на переопределение зависимости `app.dependency_overrides[get_session] = ...` (стандартный FastAPI-паттерн) — правка затронет каждый тестовый файл, а не одну точку, это нужно учесть в оценке объёма шага.

`pool_pre_ping=True` — обязателен, т.к. соединение теперь живёт долго (на уровне процесса), нужно переживать рестарты Postgres/обрыв сети без падения запросов.

## 5. Кэш для публичного просмотра расписания — Redis

Пересмотрено: при ожидаемом пиковом burst ~1k rps горизонтальное масштабирование пойдёт через несколько uvicorn/gunicorn-**воркеров** (отдельные процессы), а не через переписывание на `asyncpg` (см. раздел 9 — async по-прежнему не делаем, это отдельное и куда более дорогое решение). При нескольких воркерах in-memory `TTLCache` не годится: у каждого воркера была бы своя копия кэша, и инвалидация после правки оператора в одном воркере не была бы видна остальным — они бы до истечения TTL отдавали устаревшее расписание. Поэтому кэш сразу выносим в Redis — общий для всех воркеров, инвалидация мгновенно видна всем.

Дополнительная причина — страница публичного просмотра меняется с одной общей "последней недели" на поиск по конкретной группе/преподавателю. Ключ кэша поэтому не глобальный, а составной: `schedule:{entity_type}:{entity_id}:{week}` (`entity_type` — `group`/`teacher`). Множество ключей конечное и небольшое (по числу групп/преподавателей × видимых недель), а не произвольно растущее — это не "сложнее кэшировать", просто другая форма ключа.

`core/cache.py` — тонкая обёртка над `redis-py` (sync-клиент, т.к. остаёмся на sync-стеке):

```python
class ScheduleCache:
    def __init__(self, client: Redis, ttl_seconds: int = 45) -> None: ...
    def get_or_set(self, entity_type: str, entity_id: int, week: int, factory: Callable[[], T]) -> T: ...
    def invalidate(self, entity_type: str, entity_id: int, week: int) -> None: ...
```

Использование в `services/schedule_editor/service.py`: чтение по группе/преподавателю на конкретную неделю проходит через `cache.get_or_set(...)`; любая мутация (`create_lesson`/`update_lesson`/`delete_lesson`) после успешного `commit` инвалидирует **только** затронутые ключи — `group_id`/`teacher_id` у изменённого занятия уже известны на момент мутации, так что инвалидация получается точнее, чем при одном общем ключе "последняя неделя". Сериализация значения — JSON (Pydantic `model_dump_json()`/`model_validate_json()`), не pickle.

Инфраструктура: контейнер `redis` в `docker-compose.yml` (образ `redis:7-alpine`, без персистентности — это чистый кэш, потеря на рестарте не критична), URL через `.env` (`REDIS_URL`), подключение читается в `core/config.py` аналогично `DATABASE_URL`.

## 7. План внедрения (инкрементально, без одной гигантской ветки)

Порядок важен — каждый шаг оставляет код в рабочем состоянии:

1. **`db/engine.py` + `Depends(get_session)`** — самое важное и при этом изолированное изменение. Переключить все роутеры. Прогнать тесты, поправить `conftest.py`.
2. **Контейнер `redis` в compose + `core/cache.py` (Redis-клиент) + кэш на эндпоинтах публичного просмотра по группе/преподавателю** — независимо от остального, быстрый выигрыш под нагрузку. Если к моменту этого шага страница просмотра ещё не переведена на поиск по группе/преподавателю — кэшировать текущий "latest week" эндпоинт с ключом по неделе, потом при переводе страницы заменить схему ключа на `(entity_type, entity_id, week)` без изменения интерфейса `ScheduleCache`.
3. **Миграция с индексами** — отдельный PR, не блокирует остальное.
4. **Вынос репозиториев по одному домену за раз**, начиная с `groups`/`rooms`/`teachers`/`time_profiles`/`users` (самые маленькие, переносятся в папки `services/<domain>/{service,repository,mappers}.py` почти механически — это даёт шаблон).
5. **`schedule_editor`** — самый большой и рискованный, делать последним, с регрессионными тестами на каждом шаге: сначала выделить `repository.py` (просто переместить SQL-запросы, не меняя поведение), потом `mappers.py` (вынести построение `ScheduleProblemResponse`/`LessonMutationResponse` из бизнес-логики), потом по желанию выделить `problems.py` отдельно от мутаций занятий.
6. **`import_schedule`** — аналогично п.5, но меньше по объёму.

## 8. Схема БД: отказ от хранения сырого JSON

Проверил `7.json` (реальный формат импорта) и то, как `raw_payload`-поля используются в коде. Вывод: интуиция верна — сейчас в БД пишется заметно больше, чем нужно, и часть этого — мёртвый груз.

### 8.1. `ScheduleImport.raw_payload` — хранит весь импортированный файл целиком, нигде не читается

`services/import_schedule/service.py:54-57`:

```python
import_record = ScheduleImport(
    source_path=source_path,
    raw_payload=payload if isinstance(payload, dict) else {"documents": payload},
)
```

Сюда падает **весь** `7.json` (1.3 МБ на один импорт недели). Проверено по всей кодовой базе (`grep -rn "ScheduleImport"`) — это поле не читается ни одним сервисом, ни одной схемой ответа, ни фронтендом. Чистая запись в один конец. При импорте раз в неделю на протяжении учебного года это +1.3 МБ×~40 = ~50 МБ в JSON-колонке без какой-либо пользы, плюс лишняя нагрузка на TOAST/бэкапы/репликацию Postgres.

**Решение**: убрать `raw_payload` из `ScheduleImport` полностью. Если когда-нибудь понадобится отлаживать конкретный импорт — хранить сырой файл в файловой системе/object storage (S3-совместимом) по пути `source_path`, не в строке БД. Поля `timetable_count`/`group_count`/`lesson_count`/`empty_day_count`/`imported_at` остаются — это и есть нужный смысл записи об импорте.

### 8.2. `Lesson.raw_payload` — почти весь набор полей уже есть в нормализованных колонках

Структура одного занятия в `7.json`:

```json
{
  "subject": "Химия",
  "type": "",
  "subgroup": 0,
  "time_start": "08:00",
  "time_end": "09:30",
  "time": 1,
  "week": 7,
  "date": "23-02-2026",
  "teachers": [{"teacher_post": "", "teacher_name": "...", "teacher_id": "38364"}],
  "auditories": [{"auditory_name": "13/2"}],
  "Lesson_ID_Num": "1_7_7"
}
```

Сопоставление с моделью `Lesson` (`models.py:139-166`) и парсингом (`import_schedule/service.py:79-98`):

| Поле JSON | Куда уже парсится |
|---|---|
| `subject` | `Subject.source_name` → `subject_id` |
| `type` | `lesson_type` |
| `subgroup` | `subgroup` |
| `time_start`/`time_end` | `start_time`/`end_time` |
| `time` | `time_slot` |
| `week` | `week_number` |
| `date` | `lesson_date` (+ `weekday` из `day_payload`) |
| `teachers[0].teacher_id`/`teacher_name`/`teacher_post` | `Teacher.source_teacher_id`/`source_name`/`post` → `teacher_id` |
| `auditories[0].auditory_name` | `Room.source_name` → `room_id` |
| `Lesson_ID_Num` | `source_lesson_id` |

То есть **весь** объект уже раскладывается по нормализованным колонкам — `raw_payload=lesson_payload` (строка 98) сохраняет копию того, что и так лежит в строке по частям. На ~300k строк `lessons` за год это заметный лишний объём (JSON-блоб на каждую строку — обычно тяжелее суммы нормализованных колонок) без новой информации.

Уточнение по граничному случаю с несколькими преподавателями: проверено на реальном `7.json` (2218 занятий) — записей, где у одного занятия `teachers`/`auditories` содержит больше одного элемента, **0**. Сценарий "два преподавателя на одну пару у группы", который реально показывается как предупреждение на странице "Проблемы" (`group_slot_multiple_teachers`, `schedule_editor/service.py:644`), детектируется по-другому и без потерь — он сравнивает **разные строки `Lesson`** (разные top-level записи в `day_payload["lessons"]`, например подгруппы иностранного языка, каждая со своим `Lesson_ID_Num` и `teacher_id`) в одном `time_slot` у одной группы; каждая такая запись импортируется как отдельная полноценная строка `Lesson`, ничего не теряется.

Реальная (но непроверенная на текущих данных) потеря — внутри **одной** JSON-записи занятия `_get_or_create_teacher`/`_get_or_create_room` берут только `teachers[0]`/`auditories[0]`, остальные элементы списка не читаются вообще и не попадают ни в одну колонку. Формат это допускает, но в имеющихся данных такого не встречается — это нереализованный кейс формата, а не активный баг с потерей реальных данных.

Отдельная проблема — `raw_payload` используется как **второй источник истины** там, где должна быть достаточна одна нормализованная колонка: `_is_additional_lesson`/`_is_class_hour_lesson` (`schedule_editor/service.py:610-630`) проверяют `lesson.lesson_type` **и** `raw_payload.get("type")` **и** `raw_payload.get("subject")` **и** `Subject.source_name` — четыре источника для одной классификации "это доп.занятие/классный час или обычная пара". Это симптом, что `raw_payload` используется как подстраховка вместо того, чтобы доверять собственной нормализации при импорте.

**Решение**:
1. Убрать `raw_payload` из `Lesson` (новая alembic-миграция, `DROP COLUMN`).
2. Привести `_is_additional_lesson`/`_is_class_hour_lesson` к одному источнику — `lesson.lesson_type` (он уже заполняется из `type` при импорте) плюс при необходимости `Subject.source_name` как фолбэк для исторических данных, где `type` пуст (в примере выше `"type": ""` для обычной пары — это нормально, проверка по `subject.source_name == "Классный час"` уже работает корректно и без `raw_payload`).
3. Несколько преподавателей/аудиторий в одной JSON-записи занятия — в текущих данных не встречается (проверено на `7.json`), поэтому отдельную таблицу `lesson_teachers`/`lesson_rooms` сейчас не заводим. Достаточно зафиксировать явно (комментарий в `_get_or_create_teacher`/`_get_or_create_room` + тест), что берётся только первый элемент списка и это осознанное ограничение — если в будущем формат экспорта начнёт присылать несколько преподавателей на занятие, придётся пересмотреть.

### 8.3. `AuditLog.payload` — оставляем как есть

Это не часть проблемы: журнал изменений по дизайну должен хранить слепок payload правки (для истории действий оператора), это разумное использование JSON-колонки, отдельная история данных, а не дублирование уже нормализованных таблиц.

### 8.4. Миграция данных

Обе колонки (`ScheduleImport.raw_payload`, `Lesson.raw_payload`) убираются в одной alembic-миграции **после** того, как шаг 8.2.2 (переход классификации на `lesson_type`/`Subject.source_name`) подтверждён regression-тестами на текущих данных — то есть сначала переписать код, прогнать тесты и (если есть продовые данные) сверить результат линтера проблем до/после на реальном дампе, потом дропать колонки. Откат (`downgrade`) на дроп колонки данные не восстановит — это нужно явно отметить в docstring миграции, как и для `0010_remove_empty_day_class_hours`.

## 9. Что сознательно не делаем сейчас

- Не переходим на `async def`/асинхронный SQLAlchemy (`asyncpg`) — при ожидаемом burst ~1k rps горизонтальное масштабирование через несколько sync-воркеров дешевле и менее рискованно, чем переписывание всего слоя данных и роутеров на async; sync-стек на psycopg отпускает GIL во время ожидания I/O так же, как async, разница — в количестве процессов, не в модели конкурентности одного процесса. Возвращаемся к этому решению, только если нагрузочный тест покажет упор именно в размер threadpool/число воркеров, не закрываемый добавлением воркеров и Redis-кэшем.
- Не добавляем `relationship()` в модели — repository-слой может агрегировать запросы (`selectinload`/ручные batched-запросы) без ORM-relationships, если это понадобится при оптимизации `problems.py`.
- Не вводим автоматическую проверку границ слоёв (линтер импортов) — соблюдение конвенции из раздела 2 — вопрос код-ревью, не тулинга, на текущем размере проекта.

## 10. Горизонтальное масштабирование (несколько воркеров)

При нескольких uvicorn/gunicorn-воркерах на один процесс остаётся актуальным раздел 4 (`pool_size`/`max_overflow` в `db/engine.py`) — это лимиты **на воркер**, так что суммарное число соединений к Postgres растёт пропорционально числу воркеров и должно быть сверено с `max_connections` Postgres при выборе количества воркеров. Кэш (раздел 5) уже общий через Redis, так что эта часть не блокирует переход на несколько воркеров.

## 11. Нагрузочное тестирование (~1k rps пик)

Все решения по разделам 4/5/9/10 (пул соединений, Redis-кэш, отказ от async, число воркеров) приняты на основе рассуждений, а не измерений — раздел 9 явно завязан на "пока нагрузочный тест не покажет иное". Нагрузочный тест нужен **до**, а не после выкладки в прод, и обязателен перед тем, как считать вопрос масштабирования закрытым.

### 11.1. Цель и профиль нагрузки

- Целевой пик: ~1k rps кратковременным всплеском (между парами/в начале смены), а не как устойчивая средняя нагрузка.
- Эндпоинты под тестом — публичный просмотр расписания (после перевода на поиск по группе/преподавателю, раздел 5): большинство запросов читают кэш-попадание по уже прогретым ключам (несколько сотен студентов одной группы запрашивают один и тот же `(entity_type, entity_id, week)` в узком окне), но профиль должен включать и долю кэш-промахов (новые группы/недели, TTL-протухание), не только повторные хиты — иначе тест не проверяет нагрузку на Postgres.
- Отдельно — холодный старт кэша (первый запрос пика после рестарта/инвалидации) и поведение под одновременной мутацией (оператор правит расписание во время пика читателей) — это сценарий, где Redis-инвалидация и пул соединений нагружаются одновременно.

### 11.2. Что измеряем

- p50/p95/p99 latency публичных read-эндпоинтов под целевым rps.
- Процент ошибок (5xx, таймауты) — целевое значение 0 при заявленном пике.
- Насыщение пула соединений Postgres (`pool_size`/`max_overflow` из раздела 4) — число активных/ожидающих соединений по `pg_stat_activity` во время теста.
- Hit/miss rate Redis-кэша и его собственная latency под нагрузкой.
- CPU/память каждого uvicorn-воркера — чтобы понять, сколько воркеров реально нужно на узел.

### 11.3. Когда запускать

После шага 1 (engine/pool) и шага 2 (Redis-кэш) из раздела 7 — тестировать имеет смысл только когда обе ключевые меры уже на месте, иначе тест просто подтвердит уже известную проблему (пересоздание соединений на запрос) и не даст новой информации. Повторить тест после перевода страницы просмотра на поиск по группе/преподавателю (раздел 5) — схема кэш-ключей меняется, профиль попаданий/промахов меняется вместе с ней.

### 11.4. Критерий принятия

Конфигурация (число воркеров, `pool_size`, TTL кэша) считается достаточной, если целевой пик ~1k rps держится с p99 в пределах нескольких сотен миллисекунд и без 5xx/таймаутов на тестовом окружении, сопоставимом по ресурсам с продом. Если тест показывает упор именно в threadpool/число воркеров, не закрываемый их увеличением и Redis-кэшем — это и есть триггер для пересмотра решения "не переходим на async" из раздела 9, а не повод переходить на async заранее.

### 11.5. Инструменты

Конкретный инструмент (`locust`/`k6`/`wrk` и т.п.) и сценарии запроса — на этапе реализации, не часть этого архитектурного плана; важна сама обязательность шага и метрики из 11.2, а не выбор библиотеки.

### 11.6. Результат

Нагрузочный тест проведён (после шагов 1–2 из раздела 7): ~1.2k rps, p99 = 172ms, без 5xx/таймаутов — критерий принятия из 11.4 выполнен с запасом относительно целевого пика ~1k rps. Async-переход (раздел 9) остаётся неактуальным.

Уточнение: этот прогон не покрывал сценарий "холодный старт кэша под конкурентной нагрузкой" из 11.1 (TTL-протухание/инвалидация одновременно с читателями) — именно там позже нашёлся баг, см. 11.7.

### 11.7. Найденные баги и фиксы

**Cache-miss thundering herd exhausting DB pool** (найден 2026-07-02 повторным стресс-тестом `/schedule/public/latest-week`, целенаправленно проверявшим сценарий 11.1, не покрытый прогоном 11.6; исправлен в том же сеансе).

- Симптом: `ScheduleCache.get_or_set` (`apps/api/app/core/cache.py`) не имел защиты от одновременного пересчёта на промахе кэша. Публичный эндпоинт использует один глобальный ключ (`"latest"`) на всех читателей, поэтому протухание TTL (45s) под конкурентной нагрузкой — не редкий edge-case, а гарантированный сценарий ровно в пиковые окна (начало смены/между парами), под которые рассчитана система.
- Механизм отказа: все параллельные запросы одновременно ловили cache miss и одновременно открывали сессии БД; пул (`pool_size=10`/`max_overflow=20` = 30 соединений, раздел 4) исчерпывался почти мгновенно, остальные запросы висели полные 30s (таймаут чекаута из пула) и падали с `500`.
- Репродукция до фикса: удаление ключа кэша + 50 параллельных запросов → 40/50 `500 Internal Server Error`, зависание 60+ секунд; `ab -n 5000 -c 100` обрывался на середине в момент протухания TTL.
- Фикс (коммит `90bb24e`): single-flight пересчёт через короткую Redis-блокировку (`SET NX PX` + безопасный релиз по токену через Lua-скрипт). Только держатель лока вызывает `factory()` и пишет кэш; остальные ждут его результат опросом и переключаются на прямой расчёт только если держатель не успел за `lock_timeout_seconds` — это ограничивает худший случай сверху вместо неограниченного зависания на исчерпании пула.
- Регрессионные тесты: `apps/api/tests/test_cache.py` (в т.ч. симуляция 20 конкурентных потоков — `factory()` вызывается ровно 1 раз).
- Проверка после фикса: та же репродукция → 50/50 `200 OK`; `ab -n 3000 -c 100` через живое протухание TTL → 0 failed requests. Повторено после чистой пересборки контейнеров (`docker compose down && up --build`) — поведение стабильно.
